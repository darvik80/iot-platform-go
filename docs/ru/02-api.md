# REST API

Все эндпоинты на `/api/v1` (кроме нескольких корневых, перечисленных в [Служебных эндпоинтах](#служебные-эндпоинты)). Авторизация: `Authorization: Bearer <JWT>` или `Bearer <API-токен>`.

WebSocket для real-time обновлений: `GET /api/v1/ws?token=<jwt>` — JSON-сообщения `{ "event", "data" }` только по активному аккаунту токена. `Origin` браузера должен совпадать с хостом платформы, хостом из `PUBLIC_BASE_URL` или `localhost` (клиенты без `Origin` принимаются).

Все пути с `{id}` разрешаются внутри активного аккаунта: ID устройств, продуктов, прошивок, привязок плагинов и внешних плагинов других аккаунтов дают `404`.

Требуемая роль указана у эндпоинтов: **public** (без авторизации), **member** (любой участник активного аккаунта), **write** (`admin` или `operator`), **admin**. Если не указано иное, чтение доступно любому участнику, а изменения требуют write.

## Аутентификация

### `GET /auth/config`

Публичный. Возвращает флаги: `register_enabled`, `require_email_verify`, `google_enabled`.

### `POST /auth/register`

```json
{ "login": "jdoe", "email": "jdoe@example.com", "password": "secret123", "display_name": "Jane" }
```

Логин: `^[a-zA-Z][a-zA-Z0-9._-]{2,31}$`. Опционально `account_slug` (иначе генерируется из логина). Регистрация создаёт личный аккаунт, в котором новый пользователь — `admin`. `REGISTER_DEFAULT_ROLE` (по умолчанию `admin`) записывается только в глобальное поле `role` пользователя.

### `POST /auth/login`

```json
{ "email": "admin@example.com", "password": "<password>" }
```

Поле `email` принимает **логин или email**. Возвращает `{ "token": "<jwt>" }`.

Ограничения частоты (в памяти процесса): `login`, `register`, `resend-verification` и `check-slug` — до 20 запросов подряд с одного IP, затем один раз в 3 с; после 5 неудачных входов для одного логина/email дальнейшие попытки получают `429` (с `Retry-After`), пока не восстановится лимит — одна попытка в минуту.

Подробнее: [03-auth.md](03-auth.md).

## Продукты

Продукт — архетип устройства. Определяет RPC-методы, метрики телеметрии и атрибуты для всех устройств этого типа.

| Метод | Путь |
|-------|------|
| GET | `/products` |
| POST | `/products` |
| GET | `/products/{id}` |
| PUT | `/products/{id}` |
| DELETE | `/products/{id}` |
| POST | `/products/{id}/esp-defaults` |

`POST /products/{id}/esp-defaults` (write) заново применяет к продукту пресетные ESP-методы и метрики, сохраняя специфичные для продукта.

Тело запроса:

```json
{
  "product_id": "esp32-cam",
  "name": "ESP32-CAM",
  "description": ""
}
```

Подробнее о схеме продукта (методы, метрики, атрибуты): [09-product-schema.md](09-product-schema.md).

## RPC

### Вызов метода

`POST /devices/{id}/rpc`

```json
{ "method": "reboot", "params": { "delayMs": 1000 }, "timeout_ms": 30000 }
```

По умолчанию запрос ждёт ответ устройства (до `timeout_ms`, иначе — таймаут платформы по умолчанию). `?wait=0` — fire-and-forget.

**Механизм корреляции:** платформа выдаёт последовательный целочисленный `request_id` и сохраняет связь `{request_id → HTTP-канал}` в памяти (с таймаутом). `request_id` помещается в поле `id` MQTT-сообщения (стандарт JSON-RPC). Устройство копирует `id` из запроса в ответ. Платформа сопоставляет ответ с ожидающим запросом по `request_id` и отправляет HTTP-ответ клиенту.

Подробнее о протоколе: [04-mqtt.md → RPC](04-mqtt.md#rpc).

### История

`GET /devices/{id}/rpc` — список предыдущих RPC-вызовов.

## Мониторинг

Реализован в **v1.9.0**: дашборды аккаунта, запросы метрик, правила алертов и доставка уведомлений. Это отдельная функция, не [дашборд устройства](#дашборд-устройства) / плагин `metrics-dashboard`. Настройка и семантика доставки: [Эксплуатация → Мониторинг](11-operations.md#monitoring).

Все пути ниже указаны относительно **`/api/v1/monitoring`** и ограничены активным аккаунтом токена. Приостановленным аккаунтам доступ запрещён (`403`). `member` включает viewer; `write` означает admin/operator. **Любой доступ к каналам, даже чтение, требует admin.** ID ресурсов/устройств — внутренние числовые ID, не MQTT-имена устройств.

### Дашборды и виджеты

Пример `POST /api/v1/monitoring/dashboards` (устройство `1` должно принадлежать активному аккаунту):

```json
{
  "name": "Plant room",
  "widgets": [{
    "id": "temperature-line",
    "title": "Temperature",
    "type": "line",
    "sources": [{"device_id": 1, "key": "temperature", "label": "Room", "color": "#3d9cf0"}],
    "window_seconds": 3600,
    "aggregation": "avg",
    "width": 6,
    "min": 0,
    "max": 100
  }]
}
```

Сохранённый объект содержит `id`, `account_id`, `name`, `version` (изначально `1`) и `widgets`. Раскладка хранится в SQLite/PostgreSQL; данные виджетов запрашиваются, а не сохраняются снимком.

Для `PUT /dashboards/{id}` передайте `name`, **текущую `version`** и **полный массив `widgets`**. Обновление заменяет все виджеты и увеличивает версию. При `409` заново запросите полный дашборд, повторно примените правки и отправьте новую версию. Не сохраняйте краткий объект из списка как полный дашборд: его пустой `widgets` удалит раскладку.

- Не более 50 дашбордов/аккаунт, 24 виджетов/дашборд и 1–8 различных источников `(device_id, key)`/виджет. ID виджетов должны быть уникальны внутри дашборда.
- `type`: `line`, `bar`, `stat`, `gauge`, `table`; `aggregation`: `avg`, `min`, `max`, `sum`, `last`; `width`: `6` или `12`.
- `window_seconds`: `60..2678400` (31 день); для gauge требуется `min < max`; цвета источников — шестизначный hex (`#RRGGBB`, по умолчанию `#3d9cf0`).
- Для line/bar/gauge и числовых агрегатов используйте числовые источники; `last` также поддерживает булевы/текстовые значения в stat/table. Мастер проверяет совместимость типов; числовые агрегаты API игнорируют нечисловые строки.
- `/metrics` перечисляет реально полученные ключи телеметрии (до 1000/устройство), не объявления схемы продукта. `kind` — `number`, `boolean` или `text`; `last_seen` — время приёма в Unix-миллисекундах.

### Запрос виджета

`POST /api/v1/monitoring/query` принимает полный виджет и необязательные `from`/`to` в Unix-миллисекундах:

```json
{
  "widget": {
    "id": "temperature-stat", "title": "Average temperature", "type": "stat",
    "sources": [{"device_id": 1, "key": "temperature", "label": "Room", "color": "#3d9cf0"}],
    "window_seconds": 3600, "aggregation": "avg", "width": 6, "min": 0, "max": 100
  },
  "from": 1700000000000,
  "to": 1700003600000
}
```

Иллюстративный ответ `200` при наличии сэмплов:

```json
{
  "from": 1700000000000,
  "to": 1700003600000,
  "series": [{
    "device_id": 1, "key": "temperature", "label": "Room", "color": "#3d9cf0",
    "points": [{"ts": 1700003599000, "value": 23.5}]
  }]
}
```

Пропущенный/нулевой `to` означает «сейчас»; пропущенный/нулевой `from` — `to - window_seconds * 1000`. Требуется `0 <= from < to`, интервал не более 31 дня и `to` не более чем на 60 секунд впереди серверного времени. Запросы используют временные метки измерений.

В каждой серии до **240** агрегированных точек по всему интервалу, а не просто последние 240 сэмплов. Stat/gauge возвращают один агрегат за всё окно на источник. `ts` точки — время последнего участвующего измерения; при `last` поле `value` может быть числом, булевым значением или строкой. Отсутствие данных даёт `points: []`, **не ноль**. Числовые агрегаты используют числовые сэмплы; `last` выбирает последнее измерение в каждом интервале агрегации.

### Правила алертов

Пример `POST /api/v1/monitoring/rules` (только события, пока не выбраны каналы):

```json
{
  "name": "High temperature", "device_id": 1, "metric": "temperature",
  "kind": "threshold", "operator": "gt", "threshold": 80, "recovery": 75,
  "for_seconds": 30, "missing_seconds": 300, "cooldown_seconds": 300,
  "enabled": true, "channel_ids": []
}
```

Ответ добавляет `id`, `account_id`, `state` и `since` (Unix ms). `PUT /rules/{id}` принимает полную конфигурацию правила, не частичный патч; состоянием и его временем управляет сервер. Клиентского поля версии у правил нет.

| Поле / вид | Контракт |
|------------|----------|
| `threshold` | Требует `metric`, числовые данные и `operator` `gt` / `lt`. `gt`: срабатывание выше `threshold`, восстановление при/ниже `recovery`; `lt`: срабатывание ниже, восстановление при/выше. Порог восстановления направлен к норме |
| `no_data` | Нет данных по времени приёма в течение `missing_seconds`; пустой `metric` охватывает любую телеметрию устройства |
| `offline` | Пустой `metric`; условие выполняется при статусе offline **или** устаревшем `last_seen` |
| `for_seconds` | `0..604800`; по умолчанию `0` — немедленное срабатывание при следующей подходящей проверке |
| `missing_seconds` | `1..604800`; пропуск/ноль означает `300`; также управляет свежестью threshold, хотя форма threshold его скрывает |
| `cooldown_seconds` | `60..604800`; пропуск/ноль означает `300`; интервал повторов при firing |
| `channel_ids` | Различные ID каналов этого аккаунта; пустой список — только события. Не более 100 правил/аккаунт, 20 каналов/аккаунт |

`missing_seconds` — **не** отсрочка после отключения: offline-статус может выполнить условие сразу. Для устойчивого offline задайте `for_seconds`. Threshold требует свежего времени измерения и приёма; устаревшие/нечисловые сэмплы не восстанавливают firing и не вызывают повторные уведомления. Порядок по времени измерения не даёт запоздавшему старому сэмплу восстановления заменить более новое аварийное измерение.

Состояния `normal`, `pending`, `firing`, `resolved` сохраняются при перезапусках. Отсутствие пригодных пороговых данных, исчезновение условия или достаточно долгий перерыв в проверках прерывают удержание pending. Отключённые правила/устройства и приостановленные аккаунты не проверяются и не отправляют уведомления; pending сбрасывается. Обновление правила сбрасывает состояние в `normal`, увеличивает внутреннюю ревизию и отменяет доставки в очереди от прежней конфигурации. Проверки идут на сервере каждые 5 секунд независимо от обновления браузера.

### Каналы уведомлений

`POST /api/v1/monitoring/channels`: замените заглушку своим токеном бота; это **не** рабочие учётные данные.

```json
{
  "name": "Duty chat", "kind": "telegram", "destination": "@plant_alerts",
  "enabled": true, "secret": "<BOT_TOKEN>"
}
```

Форма ответа со скрытым секретом (`201`; поле `secret` не возвращается):

```json
{
  "id": 7, "account_id": 1, "name": "Duty chat", "kind": "telegram",
  "destination": "@plant_alerts", "enabled": true, "has_secret": true
}
```

Telegram принимает числовой chat ID или `@channel`; бот должен иметь право писать туда. Токены шифруются AES-GCM ключом, производным от `JWT_SECRET`, с привязкой к аккаунту/каналу. `PUT /channels/{id}` передаёт конфигурацию канала; пустой/пропущенный `secret` сохраняет существующий Telegram-токен. После ротации `JWT_SECRET` введите токены заново; автоматической миграции нет.

Для email используйте `kind: "email"`, один email-адрес в `destination` и не передавайте секрет. Отправка использует существующие YAML-настройки `email.*` / SMTP-переменные окружения; `EMAIL_MODE=log` даёт ошибку доставки уведомления, а не статус sent. См. [настройку SMTP/TLS](11-operations.md#monitoring).

Само сохранение не отправляет тест, но включённое правило может отправить уведомление. Явный `POST /channels/{id}/test` отправляет **реальное сообщение** через включённый канал; запрос синхронный, это не доставка через очередь. Перед удалением канала уберите ссылки на него из правил (иначе `409`). Обновление канала отменяет его доставки в очереди.

### История и ошибки

Оба эндпоинта истории принимают `limit=1..500`, по умолчанию `100` (UI показывает 100). Поля события: `id`, `rule_id`, `name`, `state`, `message`, `created_at`. Поля доставки: `id`, `event_id`, `channel_id`, `status`, `attempts`, `last_error`, `next_attempt`; временные метки — Unix ms. Тексты ошибок безопасны и не раскрывают токены ботов.

Статусы очереди: `pending`, `sending`, `sent`, `failed`; не более 5 попыток с увеличением задержки и временными захватами задач. Более старая работа pending/sending для той же пары «правило/канал» блокирует новые уведомления до окончательного завершения. Доставка — **at-least-once**: неоднозначный результат транспорта может дать дубликаты, это не exactly-once. История мониторинга не очищается автоматически по сроку хранения телеметрии.

JSON-тела ограничены **128 КиБ**; неизвестные поля и лишний JSON после объекта отклоняются.

| Статус | Значение |
|--------|----------|
| `400` | Некорректные JSON/ID/конфигурация/интервал/лимит; превышена квота дашбордов (50); ссылки на чужие устройство/канал в теле правила |
| `403` | Недостаточная роль, неактивное членство или приостановленный активный аккаунт |
| `404` | Отсутствующий/чужой ресурс по ID; отсутствующее/чужое устройство виджета; тест отключённого канала |
| `409` | Конфликт версии дашборда, превышена квота правил/каналов либо удаляется канал, используемый правилом |
| `413` | Слишком большое тело запроса |
| `500` | Неожиданная ошибка сервиса или сбой доставки тестового сообщения |
