# Эксплуатация

Руководство по запуску, конфигурации и обслуживанию платформы.

---

## Конфигурация

Приоритет (первый непустой выигрывает): **OS env → `./config.yml` → `/opt/iot-platform/etc/config.yml`**. Расширение `.yaml` тоже принимается (если есть оба файла, побеждает `config.yml`). Строка лога при старте `config sources files=…` показывает, какие файлы применены; нечитаемый или некорректный файл пишется в лог как `config file ignored` с причиной.

YAML-ключи разворачиваются в имена переменных (`server.public_base_url` → `SERVER_PUBLIC_BASE_URL`, `mqtt.addr` → `MQTT_ADDR`). Переменные окружения переопределяют YAML.

Бинарник **не** читает файлы `.env` (загрузчика dotenv при старте нет). Файл `.env` работает, только если его передаёт в окружение процесса кто-то другой — Docker Compose `env_file:` или systemd `EnvironmentFile=`.

Полные примеры: `config.yml.example`, `.env.example`.

### Ключевые переменные

| Переменная | По умолчанию | Назначение |
|-----------|-------------|-----------|
| `HTTP_ADDR` | `:8080` | HTTP-адрес (дашборд + API) |
| `MQTT_ADDR` | `:1883` | MQTT TCP-слушатель |
| `MQTT_TLS_ADDR` | `:8883` | Слушатель MQTT over TLS (активен только при заданных `MQTT_TLS_CERT` + `MQTT_TLS_KEY`) |
| `MQTT_PUBLIC_PORT` / `MQTT_WS_PUBLIC_PORT` / `MQTT_TLS_PUBLIC_PORT` | порт слушателя | Порт, который сообщается клиентам (credentials устройств, Settings, статус MQTT), если он отличается от порта слушателя, например Docker `-p 11883:1883`. Слушатель не переносит |
| `BROKER_HOST_PUBLIC` | хост из `PUBLIC_BASE_URL` (мастер) / `localhost` | MQTT-хост для устройств (TCP и TLS). URL или `host:port` сводится к хосту. За Cloudflare используйте отдельное DNS-only имя — см. [12-deploy-vds](12-deploy-vds.md#cloudflare) |
| `MQTT_WS_PUBLIC_URL` | — | Полный URL MQTT over WebSocket для клиентов, например `wss://iot.example.com/mqtt` за nginx. Пусто = `ws://{BROKER_HOST_PUBLIC}:{WS-порт}/` |
| `DATABASE_DRIVER` | `sqlite` | `sqlite` \| `postgres` |
| `DATABASE_DSN` | `/opt/iot-platform/lib/platform.db` | Путь к файлу SQLite или URL PostgreSQL (`postgres://user:pass@host:5432/db?sslmode=disable`) |
| `SQLITE_PATH` | `/opt/iot-platform/lib/platform.db` | Устаревшая: файл SQLite, если `DATABASE_DSN` пуст |
| `DATA_DIR` | каталог файла SQLite (`./data` для Postgres) | Базовый каталог данных (прошивки и т. п.) |
| `OTA_DIR` | `{DATA_DIR}/firmware` | Каталог хранения прошивок |
| `PUBLIC_BASE_URL` | `http://localhost:8080` | Публичный URL (OTA, email, OAuth) |
| `JWT_SECRET` | — | Ключ подписи JWT. Если не задан или оставлен dev-значением, платформа берёт `settings.jwt_secret` из БД либо генерирует случайный и сохраняет его туда (с предупреждением в логе) |
| `TIMEZONE` | `UTC` | Часовая зона для расписаний и тихих часов |
| `TELEMETRY_RETENTION_DAYS` | `30` | Автоочистка старых данных |
| `LOG_LEVEL` | `info` | Уровень логов: `debug` \| `info` \| `warn` \| `error` |

`ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_LOGIN` и `BOOTSTRAP_ACCOUNT_*` **не** создают администратора или аккаунт — используйте мастер настройки (ниже).

`DATABASE_MAX_OPEN_CONNS` (алиас `DB_MAX_OPEN_CONNS`) читается, но сейчас **не применяется**: размер пула захардкожен в `internal/db/db.go` (SQLite — 1 соединение, PostgreSQL — 8 открытых / 2 простаивающих).

## Первый запуск: мастер настройки

Если настроенная БД пуста (нет ни пользователей, ни аккаунтов) — или БД не настроена — платформа не стартует в обычном режиме, а поднимает на `HTTP_ADDR` только **мастер настройки** (setup wizard):

- Веб-UI: `http://<host>:8080/setup` (SPA перенаправляет туда автоматически)
- API: `GET /api/v1/setup/state`, `POST /api/v1/setup/step`, `POST /api/v1/setup/apply`, `POST /api/v1/setup/generate-tls`

Шаги: **база данных** (драйвер + DSN) → **администратор** (логин, email, пароль) → **аккаунт** (slug, имя) → **SMTP** → **JWT secret** (случайное значение сгенерировано заранее) → **MQTT TLS** (пути или генерация самоподписанного CA + серверного сертификата) → **публичный URL** (`PUBLIC_BASE_URL`, `BROKER_HOST_PUBLIC`) → **применение**.

При применении мастер создаёт администратора, аккаунт по умолчанию и membership администратора, сохраняет настройки в таблицу `settings` и пишет `config.yml` в `/opt/iot-platform/etc/config.yml`, если каталог существует и доступен на запись, иначе в `./config.yml`. Затем процесс перечитывает конфиг (значения из записанного файла перекрывают env) и продолжает запуск полной платформы — перезапуск не нужен.

При старте конфигурация берётся из env → `./config.yml` → `/opt/iot-platform/etc/config.yml`; из таблицы `settings` читается только `jwt_secret` (если настоящий секрет не задан). `config.yml` пишется с правами `0600`. Если в логе есть `failed to write config.yml`, перенесите как минимум `database.*` в файл конфига или env вручную. Также проверьте, что DSN, выбранный на шаге 1, доступен на запись пользователю сервиса (мастер подставляет `/opt/iot-platform/lib/platform.db`).

**Логина по умолчанию нет** (`admin/admin` или `admin@cogitor.local` на свежей установке не существует).

> **Безопасность**: пока работает мастер, его эндпоинты **без авторизации** — кто первым откроет порт, тот и задаст пароль администратора. Запускайте мастер только в доверенной сети или через `localhost` / SSH-туннель и не публикуйте порт 8080, пока настройка не завершена. `GET /api/v1/setup/state` не отдаёт секреты (только флаги `admin_password_set` / `smtp_pass_set` / `jwt_secret_set` и DSN со скрытым паролем). После применения маршруты мастера удаляются, а `GET /api/v1/setup/state` отвечает `{"completed":true}`. `generate-tls` пишет только в каталог сертификатов по умолчанию или в относительный путь внутри рабочего каталога.
>
> Пользователь, созданный мастером, — **админ платформы** (`settings.platform_admin_user_id`): только он может смотреть и удалять всех пользователей. Самостоятельно зарегистрированные пользователи — админы только своего личного аккаунта, независимо от `REGISTER_DEFAULT_ROLE`.

## Локальный запуск

```bash
# Терминал 1 — платформа (API + MQTT); пустая БД → мастер настройки на :8080
export DATABASE_DRIVER=sqlite
export DATABASE_DSN=./data/platform.db
go run ./cmd/platform

# Терминал 2 (опционально) — Node-RED
MQTT_BROKER_HOST=host.docker.internal docker compose up -d nodered
```

- Дашборд: http://localhost:8080
- MQTT: `mqtt://localhost:1883`

### Конфликт порта 1883

Если ESP32 выдаёт `transport_read(): EOF` / `mqtt_message_receive() returned -2` — другой процесс занял `:1883` (RabbitMQ, Mosquitto, Windows WinNAT). Платформа биндится на `0.0.0.0:1883` и откажется стартовать, если порт занят. Решение: остановить другой слушатель или установить `MQTT_ADDR=:1884`.

## База данных

Выбирается через `DATABASE_DRIVER`:

- **SQLite** (по умолчанию) — pure-Go драйвер, режим WAL, `busy_timeout=5000`, одно соединение. Файл: `DATABASE_DSN` (устаревшая `SQLITE_PATH`), по умолчанию `/opt/iot-platform/lib/platform.db`.
- **PostgreSQL** — `DATABASE_DRIVER=postgres`, `DATABASE_DSN=postgres://…` (если DSN пуст, используется `postgres://localhost:5432/iot_platform?sslmode=disable`).

Общее для обоих:

- Ежечасная очистка телеметрии, событий и логов старше `TELEMETRY_RETENTION_DAYS`
- Миграции в `internal/db/migrations/` — автоприменение при старте

**Бэкап**:

- SQLite: остановить запись или использовать `sqlite3 platform.db ".backup /backup/platform-$(date +%F).db"` (безопасно при WAL).
- PostgreSQL: `pg_dump -Fc -d "$DATABASE_DSN" -f /backup/iot-platform-$(date +%F).dump`; восстановление — `pg_restore -d <db> <file>`.
- Также сохраняйте `config.yml` (в нём `JWT_SECRET`), каталог прошивок и TLS-сертификаты MQTT.

## Мониторинг (v1.9.0)

Откройте `/monitoring` в дашборде: **Дашборды**, **Алерты**, **Каналы**, **История**. Это мониторинг всего аккаунта с данными разных устройств, отдельный от плагина `metrics-dashboard` для одного устройства. Примеры запросов и ограничения — в [API мониторинга](02-api.md#monitoring).

### Доступ и хранение

- Всё относится к **активному аккаунту**; перед настройкой переключитесь в нужный аккаунт. Приостановленным аккаунтам доступ запрещён.
- `admin` и `operator` могут создавать, редактировать, переставлять и удалять дашборды/виджеты; `viewer` может их просматривать.
- Все участники могут читать правила, события и историю доставки, запрашивать данные виджетов. Только `admin` может менять правила и вообще обращаться к каналам (включая список и тестирование).
- Раскладки, правила, состояния правил и очередь уведомлений хранятся в настроенной SQLite/PostgreSQL и переживают перезапуск. Значения виджетов запрашиваются из телеметрии, а не сохраняются как кешированные снимки.

### Создание дашборда

1. Создайте именованный дашборд, затем откройте мастер виджета.
2. Выберите устройство и его **реально полученные метрики**, а не только объявления в схеме продукта. Добавьте до восьми различных источников «устройство/метрика», в том числе с разных устройств аккаунта.
3. Выберите `line`, `bar`, `stat`, `gauge` или `table`; задайте заголовок, подписи, цвета, временное окно и агрегацию (`avg`, `min`, `max`, `sum`, `last`).
4. Для line/bar/gauge и числовых агрегатов используйте числовые метрики. `last` также допускает булевы/текстовые значения в stat/table. Для gauge минимум должен быть меньше максимума.
5. Посмотрите предпросмотр, сохраните и расположите виджеты; ширина `6` — половина строки, `12` — вся строка. На узких экранах виджеты идут друг под другом.

Мастер не предложит метрику, пока не придёт телеметрия. Пустой интервал означает **нет данных**, а не ноль. Числовые агрегаты игнорируют нечисловые сэмплы; `last` выбирает последнее измерение в каждом интервале агрегации.

| Ограничение / поведение | Значение |
|------------------------|----------|
| Дашбордов на аккаунт / виджетов на дашборд | 50 / 24 |
| Источников на виджет | 1–8 различных пар «устройство/метрика» |
| Окно виджета | 60 секунд–31 день |
| Запрос серии | До 240 точек на источник, с агрегацией по всему запрошенному окну |
| Запрос stat / gauge | Один агрегат за всё окно на источник при наличии данных |

Сохранение дашборда заменяет **весь список виджетов** с проверкой текущей `version`. Если другой редактор сохранил изменения раньше, `409` означает: перезагрузите/заново запросите дашборд и повторно примените свои правки; не повторяйте вслепую старую раскладку. Соответствующие представления дашбордов, алертов и истории обновляются примерно раз в 15 секунд.

### Правила алертов

Администратор выбирает устройство, вид правила, интервалы и необязательные каналы уведомлений. Лимит аккаунта: **100 правил** и **20 каналов**.

| Вид | Условие |
|-----|---------|
| `threshold` | Свежая числовая метрика пересекает порог `gt` (больше) или `lt` (меньше); отдельный порог восстановления задаёт гистерезис |
| `no_data` | Телеметрия не поступала в течение `missing_seconds`; можно указать одну метрику или оставить поле пустым для любой телеметрии устройства |
| `offline` | Статус устройства — offline **или** его `last_seen` устарел на `missing_seconds`; метрика не используется |

Например, `gt`, порог `80`, восстановление `75`: срабатывание выше 80, восстановление при 75 и ниже; для `lt` сравнения обратные (порог восстановления должен быть не ниже порога срабатывания).

| Поле API | Значение / умолчание |
|----------|---------------------|
| `for_seconds` | Длительность удержания условия до срабатывания; `0` разрешает срабатывание сразу при следующей проверке |
| `missing_seconds` | Интервал отсутствия данных/устаревания статуса и свежести пороговой метрики; по умолчанию `300`, минимум `1` |
| `cooldown_seconds` | Интервал повторных уведомлений при firing; по умолчанию `300`, минимум `60` |

Все три длительности ограничены `604800` секундами (7 дней). Текущая форма threshold скрывает `missing_seconds`, но API его предоставляет; значение по умолчанию продолжает действовать. Форма no-data требует полученную метрику; правило для всей телеметрии устройства с пустой метрикой можно настроить через API. Cooldown не задерживает первое уведомление и восстановление и не связан с повторами неудачной доставки.

**Интервал offline — не отсрочка после отключения.** Разрыв соединения может сразу выполнить условие независимо от `missing_seconds`. Задайте `for_seconds`, чтобы требовать устойчивого offline перед срабатыванием.

Для threshold нужны свежие время измерения и время приёма. Устаревшие/отсутствующие/нечисловые данные **не** восстанавливают сработавшее пороговое правило и не служат основанием для повторного уведомления. Измерения упорядочиваются по своим временным меткам, поэтому запоздавший старый сэмпл восстановления не заменяет более новое аварийное измерение. `no_data`, напротив, использует время приёма.

Состояния правил: `normal`, `pending`, `firing`, `resolved`. Исчезновение условия, отсутствие пригодных пороговых данных или достаточно долгий перерыв в проверках сбрасывает накопление pending; отключение правила/устройства и приостановка аккаунта также сбрасывают pending. Состояние переживает перезапуск, но простой не доказывает непрерывное удержание условия.

Обновление правила сбрасывает состояние в `normal`, увеличивает внутреннюю ревизию и отменяет доставки в очереди от предыдущей конфигурации. Отключённые правила/устройства и приостановленные аккаунты не проверяются и не отправляют уведомления. Если **каналы не выбраны**, события всё равно записываются, но ничего не отправляется.

### Email-каналы (SMTP)

Используется **существующая настройка почты платформы**: переменные окружения или соответствующие YAML-ключи `email.*`; отдельного механизма SMTP для мониторинга нет.

| Переменная окружения | YAML-ключ | Настройка |
|----------------------|-----------|-----------|
| `EMAIL_MODE` | `email.mode` | `smtp` либо не задан при настроенном хосте; явный `log` отключает реальную доставку |
| `SMTP_HOST` | `email.smtp_host` | Имя SMTP-сервера; обязательно для отправки |
| `SMTP_PORT` | `email.smtp_port` | По умолчанию `587` |
| `SMTP_FROM` | `email.smtp_from` | Корректный адрес отправителя, разрешённый SMTP-провайдером |
| `SMTP_USER` / `SMTP_PASS` | `email.smtp_user` / `email.smtp_pass` | Учётные данные, если сервер требует аутентификацию |

Порт **465** использует implicit TLS. Остальные порты — STARTTLS; открытый текст разрешён только при **фактическом подключении к loopback-адресу**, а не просто к имени, похожему на локальное. Доставка через удалённый сервер без STARTTLS завершается ошибкой.

Создайте включённый email-канал с одним адресом получателя, затем явно выполните **Тест**. `EMAIL_MODE=log` означает неудачную попытку уведомления, **а не** успешную доставку/запись в лог; после повторных попыток очередь получает статус `failed`.

### Telegram-каналы

1. Получите токен бота и выберите числовой chat ID (включая отрицательный ID группы) или адрес `@channel`.
2. Убедитесь, что бот может писать туда: запустите бота в личном чате либо добавьте его в группу/канал с нужными правами публикации.
3. Администратор создаёт включённый Telegram-канал с адресом и токеном, затем явно тестирует его реальным сообщением.
4. Выберите этот канал в нужном правиле алерта.

Токен хранится зашифрованным **AES-GCM** с ключом, производным от `JWT_SECRET`, и аутентифицированной привязкой к аккаунту/каналу. API никогда не возвращает токен, только `has_secret`. Пустой/пропущенный токен при обновлении существующего Telegram-канала сохраняет прежний.

**Храните `JWT_SECRET` вместе с резервными копиями.** После его ротации сохранённые Telegram-токены не расшифровываются: введите каждый токен заново; автоматической миграции нет. Не помещайте токены в скриншоты, примеры и логи.

Само сохранение канала **не** отправляет тест, но включённое правило с этим каналом может отправить уведомление. Явное действие «Тест» отправляет реальное сообщение; отключённый канал протестировать нельзя. Перед удалением канала уберите ссылки на него из правил.

### Доставка, история и диагностика

Проверки правил выполняются **на сервере каждые 5 секунд**. Отдельный обработчик уведомлений отправляет сообщения независимо от браузера: закрытие `/monitoring` не останавливает алерты, а медленные SMTP/Telegram не блокируют проверки.

- Постоянная очередь использует `pending`, `sending`, `sent`, `failed`, временные захваты задач и не более **5 попыток**. Повторяемые ошибки обрабатываются с увеличением задержки; постоянные могут завершить доставку раньше.
- Более старые незавершённые уведомления для той же пары «правило/канал» блокируют новые до завершения или окончательной ошибки, сохраняя порядок срабатывания/восстановления.
- Отправка повторяется в пределах лимита попыток; доставка **не гарантируется**, в том числе строго один раз: неоднозначный ответ транспорта или восстановление после сбоя могут привести к дубликатам. `sent` означает приём транспортом, а не прочтение человеком.
- Обновления правил/каналов отменяют работу в очереди; перед отправкой обработчик перепроверяет доступность аккаунта, устройства, правила и канала. Уже принятое внешним сервисом сообщение отозвать нельзя.
- История показывает последние **100** событий/доставок. API принимает `limit=1..500` (по умолчанию `100`) и возвращает число попыток, безопасный текст последней ошибки и время следующей попытки.
- История мониторинга **не** очищается автоматически по `TELEMETRY_RETENTION_DAYS`; учитывайте её при планировании размера БД и резервного копирования. Срок хранения телеметрии по-прежнему влияет на запросы виджетов.

Если сообщение не пришло, проверьте активный аккаунт, включение устройства/правила/канала, выбранные каналы, удержание/cooldown и статус доставки в Истории. Для SMTP проверьте режим/хост/TLS/аутентификацию; для Telegram — адрес, права бота и смену `JWT_SECRET`. После исправления настроек осознанно выполните тест и наблюдайте новые события правил.

## OTA-обновления

1. Загрузить `.bin` на странице **OTA** (или зарегистрировать внешний URL)
2. Платформа сохраняет файл в `OTA_DIR` (по умолчанию `{DATA_DIR}/firmware`; `DATA_DIR` по умолчанию — каталог файла SQLite) и генерирует публичный URL: `{PUBLIC_BASE_URL}/ota/fw/{token}.bin`
3. ESP скачивает прошивку **без JWT** по HTTP
4. Уведомить устройство или весь продукт → MQTT `v1/me/o/upd` (короткий стиль) или `iot/v1/{product}/{device}/down/ota/update` (полный стиль)
5. Включить **Auto-OTA** на продукте — автоотправка при переподключении

`PUBLIC_BASE_URL` должен быть доступен с устройства (NAS/LAN IP, не `localhost`).

## Часовая зона

`TIMEZONE` (IANA, напр. `Asia/Bangkok`) — для расписаний и тихих часов LED-гирлянды. По умолчанию `UTC`. Плагин может переопределить через `config.tz`.

## Ротация токена устройства

1. Оператор ротирует токен в UI или API
2. Новый хеш сохраняется в БД; живая MQTT-сессия для `{product}.{device}` отключается
3. Прошивка устройства должна быть обновлена новым токеном

## Логирование

Структурированные логи в **stdout** (`slog`):

- `connect`, `disconnect`, `auth_fail`, `acl_deny`, `subscribe` — info
- `ingest` (включая телеметрию), `command`, downlink `publish` — info

Docker: `docker logs -f iot-platform-go` (имя контейнера из `deploy-docker.yml`). Debian-пакет / systemd: `/var/log/iot-platform/platform.log`.

```bash
# Включить debug-логи (Docker)
docker run ... -e LOG_LEVEL=debug ...
docker logs -f iot-platform-go
```

Дашборд → **MQTT** показывает живые сессии и ленту событий брокера.
